# Безопасность сборки, подписи и публикации

Этот документ описывает, как устроены workflow приложения и каталога, что
проверяется автоматически и что владелец настраивает вручную.

## 1. Ключи и их изоляция

| Ключ | Где хранится | Кто его получает |
|---|---|---|
| Flowseal manifest (`FLOWSEAL_MANIFEST_SIGNING_KEY`) | секрет окружения `flowseal-sign` (только `main`, одобрение владельца) | только шаг подписи job `sign` в `flowseal-manifest.yml` |
| Каталог (`CATALOG_SIGNING_KEY`) | секрет окружения `catalog-publish` репозитория каталога | только шаг подписи job `sign` в `publish.yml` каталога |

Открытые ключи закреплены в коде (`TRUSTED_KEYS`, `CATALOG_TRUSTED_KEYS`) и
лежат файлами: `keys/flowseal-manifest-public-key.b64` здесь,
`keys/catalog-public-key.b64` в каталоге. Тест проверяет, что файл и константа
совпадают.

### Flowseal manifest: четыре job

1. **build** — без ключа, токен только на чтение. Проверяет, что окружение
   `flowseal-sign` существует, требует одобрения и ограничено ветками. Затем
   скачивает официальный архив, сверяет заранее одобренный SHA-256, запускает
   тесты, собирает бандл и пишет точные байты для подписи
   (`bridge-tools canonical`). SHA-256 этих байтов передаётся дальше через
   **выходы job**, а не через хранилище артефактов. Сторонние Actions
   (`rust-toolchain`, `rust-cache`) работают только здесь.
2. **sign** — окружение `flowseal-sign`, только `main`, только ручной запуск.
   - Выполняется только `scripts/sign/sign-ed25519.mjs`, встроенным в runner
     Node: без npm и cargo, без сборки и сторонних Actions. Из репозитория
     берутся только `scripts/sign` и `keys` (sparse checkout).
   - Подписант отказывается работать, если:
     - SHA-256 payload не совпадает с выходом build;
     - версия, хеш архива или URL — не те, что одобрены;
     - ключ не соответствует закреплённому открытому ключу.
   - После подписи он сам проверяет её закреплённым ключом. Ключ сразу
     удаляется из окружения процесса и нигде не записывается.
   - Наружу уходит только `*.signed.json`.
3. **verify** — без ключа. Проверяет конверт тем же Rust-верификатором, что
   в приложении (ключи вкомпилированы), и сверяет, что внутри ровно собранный
   payload.
4. **publish** — единственный job с `contents: write`: без ключа, без checkout
   и сборки. Сверяет SHA-256 файла с выходом verify и не заменяет
   существующий релиз.

Каталог устроен так же (см. `SECURITY.md` репозитория каталога).

### Наблюдение за релизами Flowseal (`flowseal-watch.yml`)

Раз в 6 часов (и по ручному запуску) workflow спрашивает у GitHub последний
официальный релиз Flowseal. Если это не встроенная версия и для неё ещё нет релиза
`flowseal-<версия>` с манифестом, он скачивает архив, считает SHA-256, запускает ту
же проверку совместимости, что и job `build` (все стратегии должны импортироваться),
и открывает одну задачу на версию: результат проверки, хеш и команда запуска
`flowseal-manifest.yml`.

- **Ничего не подписывает и не публикует.** Ключа у него нет, подпись остаётся
  ручной и требует одобрения владельца.
- **Хеш в задаче — не проверка подлинности.** Он взят из того же источника, что и
  архив. Перед подписью владелец просматривает релиз, как и раньше.
- **Два job.** `check` — только чтение. `report` — только `issues: write`, без
  checkout и без кода проекта; в текст задачи попадают лишь проверенные по формату
  версия и хеш, журнал сборки туда не копируется.
- Закрытая задача считается решением владельца: для той же версии она снова не
  открывается.

### Что проверяется автоматически

`scripts/ci/check-workflows.mjs` по правилам `.github/workflow-policy.json`
проверяет каждый PR:

- Actions закреплены по полному SHA, рядом комментарий с версией.
- На уровне workflow нет прав записи; `contents: write` есть только у
  перечисленных publish-job. Такой job только скачивает артефакты и вызывает
  `gh` — без сборки, секретов и сторонних Actions.
- Секреты, кроме собственного `GITHUB_TOKEN` job, читает только
  перечисленный signing-job. Условия для него:
  - нужное окружение, `if: github.ref == 'refs/heads/main'`;
  - в workflow только триггер `workflow_dispatch`, нет прав записи;
  - выполняется только команда подписанта, секрет передаётся только через
    `env` шага;
  - загружается только `*.signed.json`.
- Нет `pull_request_target` и `workflow_run`, нет подстановки полей PR
  (заголовок, тело, ветка) прямо в shell.
- У каждого `actions/checkout` стоит `persist-credentials: false`.

Тесты (`scripts/ci/check-workflows.test.mjs`) доказывают, что прежние
workflow alpha.9 эта проверка отклонила бы, и разбирают каждое нарушение
отдельно.

### Как безопасно обновить закреплённый SHA

1. Найдите нужный релиз в **официальном** репозитории Action (не в форке)
   и прочитайте изменения.
2. Получите commit SHA тега. Если тег аннотированный, разверните его:
   ```sh
   gh api repos/<owner>/<action>/git/ref/tags/<tag> -q '.object.type+" "+.object.sha'
   # если type=tag:
   gh api repos/<owner>/<action>/git/tags/<sha> -q .object.sha
   ```
3. Проверьте, что этот коммит есть в репозитории Action и отвечает релизу:
   `gh api repos/<owner>/<action>/commits/<sha>`.
4. Замените SHA во **всех** workflow и обновите комментарий `# vX.Y.Z` и
   таблицу выше.
5. PR должен пройти `Security` (политика workflow) и полный CI.

Для gitleaks возьмите SHA-256 из `checksums.txt` нового релиза, скачайте
архив и сверьте сами, затем обновите `GITLEAKS_VERSION` и `GITLEAKS_SHA256`
в обоих репозиториях.

## 3. Релиз приложения (`release.yml`)

- **gate** (только чтение):
  - тег совпадает с версиями в Cargo, `package.json` и Tauri;
  - для точного коммита тега есть успешный полный CI;
  - релиз с этим тегом ещё не существует.
- **build** (Windows, только чтение, без секретов):
  - собирается ровно этот коммит (SHA, а не имя тега);
  - тесты, служба, NSIS, проверка значков;
  - `scripts/ci/verify-installer.ps1` распаковывает установщик и сверяет:
    exe и служба — те, что собраны в этом job; файлы Flowseal — по хешам
    манифеста; лицензии на месте;
  - готовит `SHA256SUMS.txt` и notes.
- **publish** (единственный job с `contents: write`):
  - перепроверяет `SHA256SUMS`;
  - проверяет, что артефакт собран из одобренного коммита и тег за время
    сборки не сдвинулся;
  - создаёт релиз одним вызовом со всеми файлами;
  - существующий релиз не заменяется: `--clobber` больше нет.
- **Пробный прогон** без публикации: `workflow_dispatch` с `dry_run: true`
  собирает и проверяет head ветки и останавливается перед публикацией.

## 4. Почта в Git-метаданных

- Локальная идентичность в рабочих репозиториях:
  `268722850+stardely62-oss@users.noreply.github.com`.
- CI-проверка `scripts/ci/check-commit-emails.mjs`:
  - разрешены только адреса GitHub noreply (и `noreply@anthropic.com` в
    `Co-Authored-By`);
  - нарушения выводятся замаскированно (`s***@g***.com`).
- Merge-коммит, который GitHub создаёт при вливании PR, подписывается
  основной почтой аккаунта, если не включена приватность (раздел 6). Он
  появляется уже после проверки PR, поэтому вливайте PR только при
  включённой приватности; CI на `main` проверит и его.

### История репозитория

Публичный репозиторий начат заново с одного коммита текущего состояния
(alpha.9 + усиление безопасности alpha.10). Старая история alpha.1–alpha.9
с её тегами, релизами и merge-коммитами хранится в отдельном приватном
архивном репозитории и сюда не переносилась. Объекты старой истории могут
сохраняться в чужих клонах, форках и кешах GitHub, поэтому гарантировать их
полное удаление нельзя; новые коммиты проверяются CI с первого push.

## 5. Права токенов

- **Workflow.** На уровне workflow `permissions: {}` или только чтение; права
  выдаются каждому job отдельно. Запись в репозиторий только у publish-job, ключи
  только у sign-job. Job `report` в `flowseal-watch.yml` может писать только задачи.
  Job `propose` в `provider-hints.yml` меняет один файл в ветке `hints/auto` и
  открывает pull request; для этого в Settings → Actions → General должно быть
  включено «Allow GitHub Actions to create and approve pull requests».
- **checkout** не сохраняет токен (`persist-credentials: false`).
- **PR.** Не получают секретов: нет `pull_request_target`, signing-workflow
  запускаются только вручную.
- **Ручной запуск.**
  - `flowseal-manifest.yml` и `publish.yml` каталога дополнительно ограничены
    `main` и одобрением окружения.
  - `release.yml` по `workflow_dispatch` без `dry_run` публикует только тег,
    у которого есть зелёный CI, и только если релиза ещё нет.
- **Токен gh на сервере разработки** — без Administration и Secrets
  (раздел 6).

## 6. Что владелец делает вручную

1. **Окружение `flowseal-sign`** (Settings → Environments → New environment):
   - Required reviewers: `stardely62-oss`; «Prevent self-review» выключен,
     иначе единственный владелец не сможет одобрить свой запуск;
   - Deployment branches and tags: **Selected branches and tags** → `main`;
   - секрет окружения `FLOWSEAL_MANIFEST_SIGNING_KEY` — seed из раздела 8.

   Без такого окружения workflow Flowseal останавливается до подписи: job
   build проверяет его настройки через API. Секрет уровня репозитория с тем же
   именем не создавайте.
2. **Приватность почты** (github.com/settings/emails): включите «Keep my
   email addresses private» и «Block command line pushes that expose my
   email». Тогда merge через веб и `gh pr merge` подписываются noreply.
3. **Запуск workflow из форков** (Settings → Actions → General → Fork pull
   request workflows): «Require approval for all external contributors».
4. **Ruleset `main protection`** для `main` (Settings → Rules → Rulesets):
   - Enforcement: Active; Bypass list пустой — правила действуют и на
     администратора;
   - Restrict deletions, Block force pushes;
   - Require a pull request before merging, 0 одобрений — один разработчик
     может вливать свои PR;
   - Require status checks to pass: `Rust core (Linux)`, `Frontend`,
     `Security — secrets, private keys, commit emails, workflow policy`,
     `Windows build, clippy, tests, installer`.
5. **Токены сервера разработки.**
   - **Повседневный** fine-grained токен только на `discord-bridge` и
     `discord-bridge-catalog`: Contents, Pull requests, Actions, Workflows —
     read/write; Metadata — read. Без Administration, Secrets, Environments.
   - **Административный** — на 1 день и только когда нужен (rulesets,
     окружения), либо настройки через веб-интерфейс.

   Публикация релизов идёт через `GITHUB_TOKEN` в Actions, поэтому
   постоянный токен с правом администратора на сервере не нужен.

5. **Ключ релизов Bridge** — нужен один раз, чтобы включить установку новых версий
   из приложения. Без него всё работает как раньше (ссылка на страницу релиза).
   - На доверенном компьютере создайте пару тем же скриптом, что и для Flowseal, но
     в **отдельный** файл: `node scripts/keys/flowseal-key.mjs generate --seed-file <защищённая папка>/app-release-seed.txt`.
     Это другой ключ: ключ Flowseal и ключ каталога релизы Bridge не подписывают.
   - Открытый ключ, который напечатает скрипт, запишите одной строкой в
     `keys/app-release-public-key.b64` и в `APP_RELEASE_TRUSTED_KEYS`
     (`crates/bridge-core/src/apprelease.rs`). Тест ядра не пропустит расхождение.
   - Создайте окружение `app-release-sign` с теми же настройками, что у
     `flowseal-sign` (Required reviewers, только `main`), и положите seed в его
     секрет: `gh secret set APP_RELEASE_SIGNING_KEY --env app-release-sign --repo stardely62-oss/discord-bridge < <защищённая папка>/app-release-seed.txt`.
   - Выпустите версию Bridge с закреплённым ключом. Обновляться из приложения
     смогут её пользователи и пользователи более новых версий.
6. **Подпись каждого релиза Bridge.** После публикации `v<версия>` и ручной проверки
   установщика запустите `app-manifest.yml` с версией и SHA-256 установщика из
   `SHA256SUMS.txt`: `gh workflow run app-manifest.yml -f version=<версия> -f sha256=<хеш>`.
   Он публикует служебный релиз `app-<версия>` с манифестом. Пока его нет, эта
   версия ставится только вручную — так релиз можно сначала проверить на себе.

## 7. Остаточные риски

- **Кеши `rust-cache` и `pnpm`.** Используются в build-job, а их пишет CI
  `main`. Отравить их может только тот, у кого есть push в `main`; в sign-job
  кеши не используются.
- **Сторонние Actions в build-job.** Закреплены по SHA, но их код исполняется
  в job, который собирает подписываемый payload и установщик. Это ограничено
  проверками в verify и publish (хеши, Rust-верификатор), но не устранено
  полностью.
- **Владелец.** Ruleset без исключений, но владелец может его выключить;
  защита от собственных ошибок, а не от компрометации аккаунта. Включите
  2FA и держите административный токен краткоживущим.
- **`dtolnay/rust-toolchain`** закреплён на ветке без тега; обновление —
  только по процедуре из раздела 2.
- **Установщик не подписан** Authenticode. Подписанный манифест релиза защищает
  установку из приложения (скачан именно тот файл, что проверил владелец), но
  предупреждение Windows о неизвестном издателе в окне UAC остаётся.
- **Ключ релизов Bridge.** Тот, кто получит его seed и сможет подменить файлы
  релиза на GitHub, сможет предложить пользователям свой установщик. Seed хранится
  только в секрете окружения `app-release-sign` и в защищённой копии владельца;
  ротация — как у ключа Flowseal (раздел 8), с выпуском версии с новым ключом.

## 8. Ротация ключа Flowseal

Ключ Flowseal подписывает манифесты `flowseal-<версия>.signed.json`. Каталог
подписывается своим ключом, его ротация описана в репозитории каталога.

### Новая пара ключей (на доверенном компьютере владельца)

Нужен Node.js 20+ и клон этого репозитория; сеть для генерации не нужна.

```sh
node scripts/keys/flowseal-key.mjs generate --seed-file <защищённая папка>/flowseal-seed.txt
```

- seed (32 байта, base64) пишется в **новый** файл, существующий не
  перезаписывается; на экран выводятся только открытый ключ и key id;
- seed никогда не коммитится, не отправляется в чат и не выводится в CI;
  его резервная копия — в менеджере паролей или другом защищённом хранилище.

Загрузка в окружение (значение читается из файла, на экран не выводится):

```sh
gh secret set FLOWSEAL_MANIFEST_SIGNING_KEY --env flowseal-sign --repo stardely62-oss/discord-bridge < <защищённая папка>/flowseal-seed.txt
```

После этого рабочий файл с seed удаляется; на SSD удаление не гарантирует
затирания, поэтому создавайте файл сразу в зашифрованном хранилище.

### Открытый ключ в коде

1. `keys/flowseal-manifest-public-key.b64` — новый открытый ключ;
2. `TRUSTED_KEYS` в `crates/bridge-core/src/manifest.rs` — тот же ключ
   (тест `the_pinned_public_key_file_is_the_trusted_key` сверяет их);
3. проверка, что seed соответствует закреплённому ключу:

   ```sh
   node scripts/keys/flowseal-key.mjs check --seed-file <файл с seed>
   ```

   выводит только `match` или `MISMATCH` с key id.

Подписант (`scripts/sign/sign-ed25519.mjs`) отказывается подписывать ключом,
открытая часть которого не совпадает с `keys/flowseal-manifest-public-key.b64`,
а Rust-верификатор принимает только ключи из `TRUSTED_KEYS`.

### Совместимость

- Подпись проверяется только при установке новой версии Flowseal. Уже
  установленные бандлы проверяются по хешам файлов и не зависят от ключа,
  поэтому ротация их не затрагивает.
- Встроенный Flowseal 1.10.4 подписанного манифеста не требует.
- Манифесты, подписанные старым ключом, новое приложение не принимает.
  Каждый нужный манифест перевыпускается новым ключом через
  `flowseal-manifest.yml`; хеш официального архива не меняется.
- Версии приложения со старым ключом не примут манифесты, подписанные
  новым: им нужно обновить приложение.
