# Архитектура Bridge

До 0.1.0-alpha.10 программа называлась Discord Bridge. Внутренние идентификаторы
(служба `DiscordBridgeHelper` с отображаемым именем «Discord Bridge Helper»,
`discord-bridge.exe`, `%ProgramData%\DiscordBridge`, каталог настроек
`io.github.stardely62.discordbridge`) сохранены ради совместимости.

## Обзор

```
┌──────────────────────────────┐  именованный канал              ┌─────────────────────────────────┐
│ discord-bridge.exe (UI)      │ \\.\pipe\DiscordBridgeHelper.v1 │ discord-bridge-helper.exe        │
│ обычный пользователь         │ ──────────────────────────────▶ │ служба Windows, LocalSystem      │
│ Tauri 2 + React              │  фиксированные команды          │ • проверка клиента (путь образа) │
│ • DiscordManager             │  JSON, ≤ 1 МБ на кадр           │ • повторная валидация стратегий  │
│ • StrategyManager            │                                 │ • проверка SHA-256 движка        │
│ • ConfigurationManager       │                                 │ • Job Object (KILL_ON_JOB_CLOSE) │
│ • NetworkDiagnostics         │                                 │ • winws.exe ── WinDivert         │
│ • FlowsealManager (UI-часть) │                                 └─────────────────────────────────┘
│ • Telegram WS Proxy (запуск) │
└──────────────────────────────┘
          │ запускает (без прав администратора)
          ├──▶ официальный Discord (Update.exe --processStart Discord.exe)
          └──▶ Telegram WS Proxy: локальный MTProto-прокси в своём Job Object,
               без службы и без IPC с ней
```

Названия в левом блоке — роли модулей `src-tauri` (так они подписаны в их
doc-комментариях), а не обязательно имена типов.

Код разделён на пять крейтов, сборку движка Telegram, приложение и фронтенд:

| Путь | Назначение |
|---|---|
| `crates/bridge-core` | Платформонезависимое ядро: схема стратегий, таблица параметров winws, валидация, безопасный парсер BAT, рендер аргументов, diff, миграции, подписанные манифесты, IP-наборы и списки, каталог наборов и его кеш, карточки сервисов, решения об обновлениях, логика Auto, атомарная запись, протокол IPC. Полностью покрыт тестами на Linux. |
| `crates/bridge-helper` | Привилегированная служба: сервер канала и авторизация (`server.rs`, `policy.rs`), транзакции (`txn.rs`), процесс winws (`engine.rs`), бандлы Flowseal (`bundles.rs`). |
| `crates/bridge-updates` | Сетевая часть проверки обновлений Bridge и Flowseal; решения принимает `bridge_core::updates`. |
| `crates/bridge-telegram` | Менеджер Telegram WS Proxy: процесс в Job Object, протокол событий, секрет, ссылка, настройки. |
| `crates/bridge-tools` | Инструменты сборки: распаковка закреплённого релиза Flowseal, генерация, подпись и проверка манифестов и каталога. |
| `telegram-proxy` | Сборка движка Telegram WS Proxy без GUI (Python, PyInstaller) из закреплённого коммита upstream. |
| `src-tauri` | Приложение: `discord/`, `strategies/`, `configuration/`, `diagnostics/`, `zapret/` (FlowsealManager, активация, Auto, обновления), `privileges/` (клиент службы), `platform/` (трей, журнал, процессы), `catalog_sync`, `services`, `telegram`, `commands` (API для интерфейса). |
| `src` | React + TypeScript интерфейс. |

## Интеграция Flowseal

Аудит релиза Flowseal **1.10.4** (2026-10-20) показал:

- 22 стратегии `general*.bat`, все вызывают `winws.exe` (zapret 1, `v72.9`) из `bin/`
  с рабочим каталогом `bin/`; `winws2` не используется.
- BAT-файлы перед запуском вызывают `service.bat`:
  `status_zapret` (проверка службы **и включение TCP timestamps** через `netsh`),
  `check_updates`, `load_game_filter` (переменные `%GameFilterTCP%`/`%GameFilterUDP%`,
  по умолчанию порт-заглушка `12`), `load_user_lists` (создание `*-user.txt` с
  заглушками, т.к. winws не принимает пустые списки).
- `lists/ipset-all.txt` в релизе — заглушка `203.0.113.113/32` (режим `none`),
  полный список лежит в `ipset-all.txt.backup` (режим `loaded`), пустой файл — `any`.
- Голос Discord: правило `--filter-udp=19294-19344,50000-50100 --filter-l7=discord,stun`
  с fake-пакетами `ACTIVE_DISCORD_UDP.bin`.

Как это перенесено в Rust:

| Flowseal | Bridge |
|---|---|
| BAT как исполняемый скрипт | BAT читается безопасным парсером → типизированная стратегия; ничего не выполняется |
| `%BIN%x.bin`, `%LISTS%x.txt` | ссылки на ресурсы по имени `{"fake": "x.bin"}`, `{"list": "x.txt"}`; путь подставляет только служба |
| `%GameFilterTCP/UDP%` | символьные переменные в портах + настройка «Игровой фильтр» (те же правила валидации) |
| `load_user_lists` | пользовательские списки в настройках → служба записывает файлы в защищённый каталог |
| IPSet switch | настройка «Какие IP идут через обход» (см. «IP-наборы» ниже) |
| `status_zapret` → `netsh … timestamps=enabled` | **только с явного согласия** пользователя: первый запуск, Диагностика, Настройки → Обход и вопрос после запуска стратегии с `fooling=ts` (команда `tcp_timestamps_needed` только читает состояние; отказ запоминается, больше не спрашиваем) |
| `service.bat install` / служба `zapret` | собственная служба `DiscordBridgeHelper`, свой процесс winws в Job Object |
| `taskkill /IM winws.exe` | остановка только своего процесса (PID + принадлежность Job Object) |

### IP-наборы (`bridge_core::ipset`)

Что попадает в `ipset-all.txt`, решает режим `IpsetMode`:

| Режим | Содержимое `ipset-all.txt` |
|---|---|
| `none` | заглушка `203.0.113.113/32` — IP-правила ничего не захватывают (умолчание Flowseal) |
| `selected` | ручные «IP через обход» + IP установленных наборов каталога |
| `flowseal` (бывший `loaded`) | полный список Flowseal `ipset-all.txt.backup` как есть |
| `flowsealPlusSelected` (по умолчанию для новых установок, с 0.1.4) | список Flowseal + выбранные IP |
| `any` | пустой файл = все адреса (расширенный, рискованный режим) |

- Источники: `UserLists::ipset_include` (ручной список) и `InstalledPack::ips`
  (наборы каталога). `lists::effective_lists` объединяет их: сначала ручные, затем IP
  наборов, дубли убираются по сети (`1.2.3.4` = `1.2.3.4/32`). Удаление набора убирает
  только его вклад, ручные IP и общие подсети других наборов остаются.
- Исключения (`ipset_exclude`) важнее всего и соблюдаются самим списком:
  - из каждой подсети точно вычитаются исключённые сети (`ipset::subtract`): `10.0.0.0/8 − 10.1.0.0/16` = 8 блоков от /9 до /16;
  - в режиме `any` при наличии исключений пишется явное «все адреса минус исключения», без исключений — по-прежнему пустой файл.

  Поэтому исключения работают и для своих и импортированных стратегий без `--ipset-exclude`. Стандартные стратегии Flowseal вдобавок ставят `--ipset-exclude=ipset-exclude-user.txt` на каждое правило с `ipset-all.txt` — это закреплено тестом на всех 22 BAT.
- Пустая выборка записывается заглушкой, а не пустым файлом (пустой файл для winws —
  «все адреса»). Режим никогда не меняется сам: установка набора с IP не расширяет обход.
- Валидация: IPv4/IPv6 и CIDR; в списках «через обход» запрещены сети шире `/8` (IPv4)
  и `/16` (IPv6) — для всех адресов есть режим `any`. Лимит 10 000 строк на список.
- Статус в интерфейсе (`ipset::ip_set_status` → `Overview.ipSets`) различает шаги:
  - набор установлен;
  - IP попадают в подготовленный `ipset-all.txt` (`prepared`, с учётом режима и исключений);
  - в активной стратегии есть включённые правила с `--ipset=ipset-all.txt` (`strategy.ipsetRules`);
  - работающий движок запущен с этой стратегией и текущей конфигурацией (`engineUpToDate`, по `config_hash`).

  «Применяются» (`applied`) показывается только при выполнении всех шагов.
- `lists::runtime_list_files` строит все runtime-списки (чистая функция, тесты на
  любой платформе); служба только записывает их в каталог поколения `gen-N/lists`,
  жизненный цикл переключения и отката не менялся.
- Старые настройки читаются без миграции: новые поля пустые по умолчанию, `loaded`
  читается как `flowseal`. Протокол IPC — версия 3.
- Умолчание `flowsealPlusSelected` действует только без файла настроек (`Settings::default`).
  У поля `ipsetMode` своё значение по умолчанию — `none`, поэтому файл, записанный до
  появления поля, режим не меняет; сохранённый режим не меняется никогда.

Тест `crates/bridge-core/tests/flowseal_fixtures.rs` берёт все 22 оригинальных BAT,
независимым «наивным» способом извлекает аргументы и сравнивает с рендером
Bridge **в точности, включая порядок**, для трёх режимов игрового фильтра.

## Стратегии

См. [docs/strategies.md](docs/strategies.md). Кратко: версия схемы `1`, глобальные
параметры (`--wf-*`) + упорядоченные правила (профили winws, разделённые `--new`).
Таблица допустимых параметров (`strategy/options.rs`) — единый источник для
валидации и визуального редактора. Неизвестные параметры отклоняются.

Встроенные стратегии строятся во время работы из оригинальных BAT активного набора
Flowseal и неизменяемы; редактирование — через копию (`origin.baseId`), доступны
«Сравнить с оригиналом» и «Восстановить оригинал». Пользовательские стратегии
хранятся отдельно (`%APPDATA%\io.github.stardely62.discordbridge\strategies\*.json`)
и не затрагиваются обновлениями Flowseal.

## Привилегии и безопасность

- UI никогда не запускается с повышенными правами.
- Служба принимает только фиксированный набор команд (`bridge_core::ipc::Request`).
  Команды «выполнить произвольное» нет. Каждое соединение начинается с `Hello`
  с версией протокола; при несовпадении версий служба отвечает ошибкой.
  - Только чтение: `Status`, `Diagnose`, `ListBundles`, `EngineLog`, `ReadBundleList`.
  - Управление: `Start`, `Stop`, `BeginTrial`, `EndTrial`, `SetTcpTimestamps`
    (только с флагом согласия), `RestoreTcpTimestamps`, `InstallBundle`,
    `SetActiveBundle`.
- Канал: `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, DACL:
  SYSTEM/Администраторы — полный доступ, интерактивные пользователи — чтение/запись
  без права создавать экземпляры канала.
- Аутентификация клиента: путь образа подключившегося процесса
  (`GetNamedPipeClientProcessId` → `QueryFullProcessImageNameW`) должен совпадать с
  `discord-bridge.exe` в каталоге установки (Program Files, запись только для админов).
  Это отсекает посторонние программы, но не является границей безопасности внутри
  одной учётной записи: процесс того же пользователя может запустить установленный
  `discord-bridge.exe` и выполнить в нём свой код. Поэтому защита строится не на
  доверии к клиенту, а на том, что служба умеет только перечисленные команды,
  сама валидирует каждую стратегию и сама строит все пути.
- Служба явно задаёт владельца канала SYSTEM; клиент проверяет, что владелец — SYSTEM или «Администраторы» (непривилегированный процесс не может создать объект ни с тем, ни с другим владельцем).
- Каждая стратегия повторно валидируется в службе; пути строятся только из имён
  ресурсов внутри защищённых каталогов.
- Перед запуском `winws.exe`, `cygwin1.dll`, `WinDivert.dll`, `WinDivert64.sys`
  открываются с запретом записи/удаления, хэшируются **через эти же дескрипторы**
  и сверяются с манифестом; дескрипторы удерживаются, пока движок работает (нет окна TOCTOU).
- winws создаётся приостановленным, помещается в Job Object с
  `KILL_ON_JOB_CLOSE` и только потом возобновляется: если служба упадёт, Windows
  завершит и winws — бесконтрольных процессов не остаётся.
- Изменяемые данные службы: `%ProgramData%\DiscordBridge` с владельцем SYSTEM и
  защищённым DACL (SYSTEM + Администраторы). Каталог, заранее созданный
  посторонним владельцем, переименовывается, а не используется.
- Bridge не меняет hosts, DNS, брандмауэр и не трогает Защитник Windows.

## Транзакционная смена стратегии (с alpha.4)

Служба (`crates/bridge-helper/src/txn.rs`) переключает движок как транзакцию:

1. **Подготовка без касания работающего движка**: валидация, проверка целостности
   бандла, материализация списков в *новый* каталог поколения
   `%ProgramData%\DiscordBridge\runtime\gen-N\lists`, рендер аргументов.
   Ошибка на этом шаге → `prepareFailed`, старый winws и его списки не тронуты.
2. Остановка старого winws, запуск нового (`Backend::start` с проверкой хэшей
   через удерживаемые дескрипторы и 1,5 с контроля).
3. При ошибке — запуск **точного снимка** предыдущего запуска (`LaunchSpec`:
   стратегия в том виде, в каком была запущена, runtime-параметры, бандл
   Flowseal и его собственный каталог списков) → `rolledBack`; если и это не
   удалось → `rollbackFailed`, обход выключен, ошибка показывается.
4. Каталог старого поколения удаляется только после успешного переключения.

Снимок не зависит от ID: правка активной стратегии с тем же ID не влияет на
откат. Хэш конфигурации (`bridge_core::strategy::config_hash`) хранится в снимке
и используется также для подтверждений голоса.

**Критерий «работает» для Auto.** Движок запущен, Discord API отвечает корректным
JSON и `gateway.discord.gg` завершает TLS. С настройкой `autoCheckYoutube`
(выключена по умолчанию) дополнительно должны ответить адреса YouTube из тестового
списка самого Flowseal (`utils/targets.txt`): `www.youtube.com`, `youtu.be`,
`i.ytimg.com`, `redirector.googlevideo.com`. Это проверка того, что соединения
устанавливаются: скорость видео и голос Discord автоматически не проверяются.
Диагностика показывает те же адреса YouTube отдельной группой; на вердикт о
Discord они не влияют.

**Пробный режим (Auto).** `BeginTrial` фиксирует текущий снимок (или «выключено»)
как базовую линию; `EndTrial{commit:false}` восстанавливает её точно. Логика
перебора (`bridge_core::auto`) заканчивает любой неуспешный сценарий — отмена,
тайм-аут, исчерпание попыток, ошибка IPC/службы — восстановлением. Брошенный
пробный режим (приложение упало) откатывается при следующем запуске приложения.
Во время Auto ручное переключение, выключение и смена Flowseal отклоняются,
выход из приложения отменяет Auto и дожидается восстановления.

## Авторизация службы (с alpha.4)

* **Аутентификация**: путь образа клиента — установленный `discord-bridge.exe`
  (каталог Program Files, запись только администраторам); личность клиента —
  из **токена** через `ImpersonateNamedPipeClient` (SID, сеанс, elevation),
  а не из PID.
* **Авторизация** (`policy.rs`): чтение статуса — любому клиенту; управление
  (старт/стоп/Auto/TCP timestamps/обновления Flowseal) — если обходом никто не
  владеет, клиент — владелец (тот же SID), сеанс владельца завершён, или клиент
  запущен с повышенными правами. На однопользовательском ПК это незаметно.
* **Ресурсы**: не более 8 одновременных клиентов, принудительное закрытие
  соединения через 90 с, кадр ≤ 1 МБ; архив обновления передаётся путём к файлу
  и читается службой **под олицетворением клиента** (только то, что может
  прочитать сам пользователь), до 64 МБ.

## Конфликты

Перед запуском служба ищет процессы `winws.exe`, `winws2.exe`, `goodbyedpi.exe`, не
принадлежащие её Job Object, и запущенные службы `zapret`, `GoodbyeDPI`, `winws1`,
`winws2`, `discordfix_zapret` (тот же список, что использует Flowseal). При конфликте
запуск не выполняется; UI объясняет причину и предлагает запуск только с явным
подтверждением. Чужое ничего не останавливается.

## Обновления

Три независимых канала:

1. **Приложение** — проверка последнего релиза этого репозитория. Фоновой установки
   нет. Установить новую версию из приложения можно, только если для неё опубликован
   **подписанный манифест релиза** (`bridge_core::apprelease`, релиз `app-<версия>`):
   - манифест — Ed25519-конверт с версией, именем, размером и SHA-256 установщика;
     ключ отдельный, не ключ Flowseal и не ключ каталога
     (`APP_RELEASE_TRUSTED_KEYS`). Версии без закреплённого ключа (до 0.1.2) манифест не
     запрашивают и обновляются вручную, со страницы релиза;
   - адреса манифеста и установщика строятся из проверенной версии, из документов они
     не берутся;
   - по кнопке и после подтверждения приложение скачивает установщик в свой каталог
     данных, сохраняет его только при совпадении размера и SHA-256 с подписанными,
     открывает файл заново с запретом записи и удаления, хеширует ещё раз через этот
     дескриптор, запускает и выходит. Права администратора запрашивает сам
     установщик (UAC); служба в установке не участвует и новых команд не получила;
   - если манифеста нет, подпись не сошлась или запуск отклонён, остаётся ручная
     установка со страницы релиза, Bridge продолжает работать.
2. **Движок и бинарники** и 3. **набор стратегий/ресурсов** поставляются вместе как
   «бандл Flowseal». Новая версия устанавливается, только если для неё опубликован
   **подписанный манифест** (Ed25519; закрытый ключ хранится в секретах GitHub
   Actions, открытый — вшит в приложение и службу). Манифест содержит SHA-256 архива
   и каждого файла; архив скачивается с официального релиза Flowseal; служба заново
   проверяет подпись и хэши, проверяет совместимость (все стратегии должны
   импортироваться) и ставит бандл в `%ProgramData%\DiscordBridge\bundles\<версия>`.
   Предыдущие версии остаются — доступен откат. Хэш из того же источника, что и
   архив, как доказательство подлинности не используется.

По умолчанию новую версию Flowseal пользователь ставит сам, кнопкой в «Обновлениях».
Настройка `autoInstallFlowseal` (выключена по умолчанию) разрешает ставить её без
вопроса — один раз за сеанс, после проверки при запуске, и только версию с
проверенным подписанным манифестом. Переключение идёт той же транзакцией с откатом.
Оно пропускается, пока идёт Auto, при выходе и если с новой версией перестанут
работать собственные стратегии пользователя (версия остаётся установленной, но
неактивной). Результат всегда показывается. Сам Bridge так не обновляется.

Подписанный манифест создаёт workflow `flowseal-manifest.yml` (ручной запуск с
указанием версии и проверенного хэша). Новые релизы Flowseal замечает
`flowseal-watch.yml`: он проверяет совместимость и открывает задачу с хэшем и
командой запуска; подписывать он не может.

Смена версии — транзакция: активировать B → перезапустить работающую стратегию
на B → при ошибке служба восстанавливает снимок на A, а приложение возвращает
активную версию A. Перед переключением показывается отчёт совместимости
пользовательских стратегий (отсутствующие fake-файлы, списки, параметры);
профили не меняются. `minAppVersion` проверяется по SemVer при установке и
активации. Если манифест получить не удалось (не опубликован, нет сети, ошибка
или лимит GitHub), приложение показывает причину, а не «рабочую» кнопку и не
«обновлений нет».

## Жизненный цикл

- **Запуск приложения**: загрузка каталога (через службу либо, если она недоступна,
  только для чтения из ресурсов) → при настройке «автоматически включать обход»
  активация стратегии → при настройке — запуск Discord.
- **Активация**: валидация → остановка своего winws → запуск → контроль 1,5 с →
  HTTPS-проверка Discord. Стратегия помечается «последней рабочей» только при
  успешной HTTPS-проверке. Если запуск не удался — возврат к предыдущей стратегии.
- **Закрытие окна**: по настройке — в трей или выход.
- **Полный выход**: по настройке «Останавливать обход при выходе» (по умолчанию да)
  winws останавливается; иначе продолжает работать под управлением службы.
- **Наблюдение**: лёгкий опрос состояния службы (5 с при открытом окне, 20 с в трее)
  для обнаружения аварийного завершения winws.

## Каталог приложений и сервисов (`bridge_core::packs`, `catalog_sync`)

Каталог — это только данные: домены, IP-сети, описания и значки. Он публикуется отдельным
репозиторием [`stardely62-oss/discord-bridge-catalog`](https://github.com/stardely62-oss/discord-bridge-catalog)
и обновляется независимо от релизов приложения.

- **Публикация.** Релиз `catalog-<serial>` содержит два файла:
  - `catalog-data.json` — наборы и значки (base64);
  - `catalog.signed.json` — Ed25519-конверт над манифестом. В манифесте `kind: discord-bridge-catalog`, `serial` (время коммита, растёт только вверх), размер и SHA-256 данных, число наборов и значков.

  Подписывает только ручной workflow в окружении `catalog-publish` с обязательным ревьюером. PR сообщества проходят лишь проверку.
- **Доверие.** Подпись проверяется ключом из `CATALOG_TRUSTED_KEYS`, отдельным от ключа манифестов Flowseal. Проверяется и вид документа. Код проверки подписи общий (`manifest::verify_signed_bytes`), ключи и назначение — разные.
- **Загрузка (Rust, не React).**
  - Манифест берётся из фиксированного `releases/latest/download/catalog.signed.json`.
  - Данные — только из релиза `catalog-<serial>` того же номера; URL из документов не используются.
  - Таймаут 20 с, лимиты применяются при чтении потока: манифест ≤ 64 КБ, данные ≤ 4 МБ.
  - Условный запрос по ETag.
  - Проверка через 15 с после старта (если включены проверки обновлений), затем каждые 6 ч и по кнопке.
- **Проверка (`verify_catalog`):**
  - подпись, вид документа, формат и схема, `minAppVersion`;
  - размер и SHA-256 данных, номер публикации, число наборов и значков;
  - каждый набор: id, версия, тексты, домены, CIDR с минимальными префиксами, https-источники;
  - каждый значок: только PNG/WebP по заголовку, ≤ 64 КБ, ≤ 512×512, SHA-256. SVG не принимается.
  - Лимиты: 500 наборов, 2000 доменов и 5000 IP на набор.
  - **Прямая совместимость (с 0.1.0-alpha.11).** Неизвестные поля набора игнорируются (строгую схему проверяет CI каталога). Набор более новой схемы не интерпретируется и не используется (`usable_packs`), остальные работают. Вложенные объекты (тексты, источники, требования) по-прежнему строгие. alpha.10 отвергает такой каталог целиком и остаётся на последнем проверенном — поэтому новые поля публикуются только после выхода версии, которая их понимает.
- **Кеш (`packs::store`).**
  - Хранятся `current.*`, `previous.*` и `state.json` (наибольший принятый `serial`, ETag, время, последняя ошибка); всего не больше ~8,2 МБ.
  - При чтении всё проверяется заново. Повреждённая текущая копия заменяется проверенной предыдущей, иначе используется встроенный снимок `resources/catalog/builtin-catalog.json`.
  - Более старый подписанный каталог не принимается (защита от отката).
  - Ошибки сети, подписи или кеша меняют только статус каталога — не настройки и не движок.
- **Установленные наборы** — снимки в `installedPacks`: версия, домены, IP, название, предыдущий снимок для отката. Установка, обновление и откат меняют только `installedPacks` через валидируемое атомарное сохранение настроек. Объединение с ручными списками и применение — прежние: `effective_lists`, `ipset`, `pendingApply`, хэш конфигурации, откат движка. winws при этом не перезапускается. Набор, исчезнувший из каталога, остаётся локально, пока его не удалят.
- **Подтверждение точного снимка (`PackConfirm`).** Окно показа и команда `pack_install` обмениваются токеном: id, версия набора, `serial` каталога (удалённого или встроенного), `pack_sha256` — SHA-256 канонического JSON набора (serde, фиксированный порядок полей) — и `installed_sha256` установленной копии, от которой посчитана разница. Под блокировкой настроек `install_confirmed` сверяет токен с текущим проверенным каталогом и настройками и сохраняет именно тот `Pack`, чей хеш только что проверен. Любое расхождение — ошибка «изменился после просмотра», настройки и движок не трогаются. React фиксирует показанный снимок и не подменяет его ответами от более нового каталога.
- **Правило версий** проверяется в репозитории каталога (`check-versions.mjs`): адреса набора меняются только с ростом `version`, относительно базовой ветки и последнего опубликованного подписанного каталога.
- **Статусы.** Каждый означает одно: входит в Flowseal / не установлен / установлен / есть новая версия / отличается от каталога. Отдельно: сохранено, но не применено; домены и IP используются работающим обходом; доступность сервиса не проверялась.
- **Порты набора (`Pack.ports`, `services::port_coverage`).** Необязательное поле
  верхнего уровня `ports: { tcp?, udp? }` — порты собственного трафика сервиса в
  синтаксисе `--filter-tcp`/`--filter-udp` (например, Photon: `udp: "5055-5058"`).
  Только описание: в winws из каталога по-прежнему ничего не попадает. Поле на верхнем
  уровне, потому что версии до 0.1.4 игнорируют неизвестные поля набора, а `requires`
  разбирают строго. Проверка: не более 32 элементов на протокол, без порта 0 и без
  переменных игрового фильтра.
  - Для активной стратегии и текущего игрового фильтра вычисляется, какие включённые
    правила обрабатывают все эти порты для адресов IP-набора: правило с
    `--ipset=ipset-all.txt` или без положительного адресного фильтра, без L7-фильтра,
    который не пропустит `unknown`, и с портами в `--wf-*`. Результат — `covered`
    (номера правил), `needsGameFilter` (покроет режим игрового фильтра, который
    сохраняет уже включённые протоколы) или `noRule`.
  - Во всех 22 стратегиях Flowseal UDP 5055–5058 к адресам IP-набора обрабатывает
    ровно одно правило — игрового фильтра по UDP; без фильтра — ни одно (закреплено тестом).
  - Набор старого каталога без `ports`, но с `requires.gameFilter`, получает только
    подсказку «нужен игровой фильтр», пока фильтр выключен.
  - `Overview.packPorts`; интерфейс показывает подсказку в карточке, в «Моих» (только
    проблемы) и в окне набора, с кнопкой включения игрового фильтра нужного режима.
    «Обрабатываются» говорит о конфигурации, не о том, что игра подключается.

## Карточки сервисов (`bridge_core::services`, `services`)

Карточка показывает три разные вещи и не смешивает их.

- **Адреса сервиса** — домены и IP из подписанного каталога (`Pack.domains`, `Pack.ips`). У встроенных во Flowseal сервисов (Discord, YouTube, Google, Cloudflare) есть `flowsealList`; они информационные и не устанавливаются.
- **Источники Flowseal** — оригинальные файлы `lists/*` активной версии Flowseal, без изменений.
  - Встроенная версия читается из ресурсов программы, версия-обновление — через службу: запрос `ReadBundleList` только на чтение, отдаёт только файлы `lists/` из манифеста бандла, частями по 384 КБ.
  - В обоих случаях SHA-256 сверяется с манифестом бандла. Ничего не скачивается.
  - Для каждого домена сервиса находится строка, которая его покрывает: точная или родительский домен; `^домен` не покрывает поддомены. Отдельно — строка исключения (`list-exclude*`), если она его снимает.
  - Числа — строки и записи — считаются по самим файлам.
- **Реальная конфигурация** — правила выбранной стратегии, которые касаются карточки:
  - по её списку (`--hostlist`; для установленных наборов — `list-general-user.txt`);
  - по доменам в правиле (`--hostlist-domains`);
  - по протоколу L7 сервиса (для Discord: `discord`, `stun`).
  - Каждое правило показывается с портами TCP и UDP (игровой фильтр подставлен) и исключениями.
  - Правила с общим IPSet (`ipset-all.txt`) показываются отдельно: это не адреса сервиса.
- **Статус применения** (`ApplyState`):
  - *известен* — адреса есть в проверенном источнике;
  - *подготовлен* — у выбранной стратегии есть правила для них, и хотя бы один домен не исключён;
  - *применяется* — работающий WinWS запущен с этой стратегией и этой версией Flowseal, нет несохранённых изменений (`pendingApply`).
  - «Доступность подтверждена» бывает только у Discord и только по свежей успешной диагностике при этой конфигурации.
- **Пересечения.** Домен, который равен домену другой карточки или набора либо является его поддоменом, помечается «также: …». Правило Flowseal одно на файл, а `effective_lists` записывает общие домены установленных наборов один раз.
- **Длинные списки** (IPSet — десятки тысяч строк) отдаются страницами с поиском на стороне Rust; интерфейс рисует только видимые строки. Копирование возвращает файл целиком без изменений.

## Telegram WS Proxy (`bridge_telegram`, `telegram`)

Локальный MTProto-прокси для Telegram Desktop — сетевой движок
[Flowseal/tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy) 1.11.4,
собранный без GUI из закреплённого коммита (`telegram-proxy/README.md`).
Это **отдельный компонент**, независимый от Zapret.

- **Процесс.** Обычный процесс пользователя: без прав администратора, без
  службы и без IPC со службой Zapret.
  - Запуск без shell, с `CREATE_NO_WINDOW`. Процесс создаётся приостановленным,
    помещается в Job Object с завершением при закрытии и только потом
    возобновляется. Так в задание попадает и Python-процесс загрузчика
    PyInstaller, и при аварии Bridge прокси завершается вместе с ним.
  - Запускается только файл, чей SHA-256 совпадает с хешем, вкомпилированным
    в `discord-bridge.exe` (`build.rs`), и с манифестом.
- **Состояние** берётся из реального процесса и его JSON-событий:
  - `notInstalled`, `stopped`, `starting`, `listening`, `error`;
  - `connected` — только пока идёт хотя бы одно соединение клиента, прошедшего проверку секрета и переданного к Telegram. Счётчик upstream `connections_active` растёт ещё до проверки секрета, а счётчики маршрутов накопительные; поэтому запускатель считает активные пересылки по функциям моста, которые upstream вызывает только после успешного рукопожатия и установленного соединения с Telegram (`relays_active`).
  - Прошлые соединения показываются отдельно, как история сеанса. Открытый порт подтверждением работы не считается. «Обмен данными с Telegram» означает, что за сеанс от серверов Telegram пришли байты.
- **Остановка.** Сначала строка `stop` и закрытие stdin (штатно), через 6 с —
  `TerminateJobObject`.
  - Неожиданный выход — состояние `error` с причиной. Если прокси до этого успел
    заработать (слушал порт) и пользователь его не останавливал, Bridge запускает
    его снова (`bridge_telegram::supervise`): не больше двух попыток, через 3 и
    20 с; счёт начинается заново после 5 минут стабильной работы. Неудавшийся
    запуск (занятый порт, повреждённый компонент) не повторяется никогда.
  - Занятый порт — ошибка: чужая программа не останавливается.
- **Независимость.**
  - Автозапуск — своя настройка `telegramProxy.autostart`, не связанная с
    `autoEnableBypass`.
  - `stopBypassOnExit` на прокси не влияет. Полный выход останавливает прокси
    всегда, закрытие в трей — нет.
  - Остановка или запуск Zapret прокси не трогает, и наоборот.
  - Сетевое пересечение возможно, и диагностика его показывает: WinWS
    обрабатывает соединения прокси к Telegram, если `telegram.org` есть в
    списках пользователя или наборов, либо IPSet содержит адреса Telegram
    (режим «все адреса»).
- **Секрет.**
  - 16 байт из CSPRNG ОС, 32 hex-символа; ссылка
    `tg://proxy?server=127.0.0.1&port=…&secret=dd…` — та же форма, что печатает upstream.
  - Хранится в отдельном файле `telegram-proxy.secret` в профиле пользователя,
    не в настройках, поэтому не попадает в экспорт.
  - На Windows у файла явный защищённый DACL без наследования: полный доступ только у пользователя, SYSTEM и администраторов. Он ставится на временный файл до записи секрета и восстанавливается при загрузке.
- **Порт ссылки.** Ссылка, «Подключить Telegram» и диагностика используют порт работающего процесса. Сохранённый, но не применённый порт показывается отдельно с просьбой перезапустить прокси.
  - Передаётся движку одной строкой stdin. Не логируется: движок и Rust
    вырезают его из журнала. В React он не передаётся.
  - Ссылку с секретом выдают только явные действия «Копировать» и
    «Подключить». `telegram_open` открывает только собственную ссылку,
    прошедшую строгую проверку: localhost, порт, `dd` + 32 hex. Если
    обработчика `tg://` в реестре нет, ссылка не открывается, вместо этого
    показывается инструкция.
- **Маршруты.**
  - По умолчанию — прямой WebSocket к Telegram, с TCP-резервом движка.
  - Резерв через узлы Cloudflare (CfProxy, HTTP/2 для медиа, свои домены
    Cloudflare и Worker) — только по явному выбору. Upstream включает его по
    умолчанию и загружает список узлов с GitHub. Использованный маршрут виден
    по счётчикам движка.
